### 開源會直接撞到的缺口

**安裝與發布**

- README 只有兩行，沒有安裝與使用說明
- 沒有發布到 PyPI，只能 clone 之後用 `uv` 執行
- 前端要自己 `npm run build`；`web/dist` 的位置是從原始碼路徑往上找的，裝成套件後會找不到
- 需要 Python 3.13 以上
- 使用者要自己裝好並登入 `gh`、`claude`、`codex`，工具沒有檢查，缺了會在執行到一半時才失敗

**平台**

- 只在 macOS 上跑過。五個模組用了平台相關的東西（訊號、檔案鎖、程序群組、`osascript`）：`recovery.py`、`daemon.py`、`cli.py`、`notifier.py`、`adapters/codex.py`
- 通知只支援 macOS

**專案本身的基礎建設**

- 這個 repo 自己沒有 CI，測試都是在本機跑的
- 沒有 CONTRIBUTING、issue 範本、變更紀錄
- 文件、註解、任務單是繁體中文，識別字與 commit 訊息是英文
- repo 是 private，授權已經是 Apache-2.0
- CLI 指令名稱 `asv` 還是暫定的

**信任模型**

- 規格明寫「只用在自己信任的 repo」，權限政策是基本防護不是安全邊界
- Claude Code 的 sandbox 與限制連網沒有生效，原因沒查明
- Codex 無法逐次攔截指令，允許連網時擋不住它自己 `git push`
- API 沒有登入，本機上的其他程式可以直接呼叫

### 已知但沒處理的行為問題

**會卡住、要人工處理的**

- PR 關閉後又重新開啟，工具不會發現，任務永遠拒絕訊息
- 重啟後確認不了遺留程序是否停止的任務會永遠顯示 Working，沒有手動結案的方法
- 準備或封存做到一半中斷，下一次會因為 branch 已存在或目錄不存在而失敗
- agent 改寫了已經 push 的 commit，下一次 push 被拒絕
- 任務超過花費上限後連手動送訊息都被拒絕，要改設定檔才能繼續

**顯示或操作不順的**

- `asv list` 把 Codex 的未知花費顯示成 `$0.00`
- 專案設定不能從介面改
- PR 合併後 worktree 不會自動清
- 沒有合併按鈕
- Diff 看不到還沒 commit 的變更
- PR 裡的 commit 訊息幾乎都是固定的 `chore(agent): save uncommitted changes…`
- 不回覆 PR 留言

**任務變多之後才會出現的**

- 每次寫入都重算所有任務的指紋；`GET /tasks` 對每個任務各查好幾次
- 斷線重連的事件補送沒有上限
- 沒有同時執行數的上限，也沒有排隊

### 沒有實測過的路徑

- 階段 1.5 的 4 項（決策第 94 筆）
- 階段 3 的 2 項：`changes_requested` 的行為、Stop 一個正在解衝突的 run
- 多個專案同時使用、大量任務、長時間不重啟

### 文件本身的狀況

- `04-phase1-tasks.md` 的驗證清單有 29 項沒有勾，但階段 1 的功能都在用。很可能是驗證過而當時沒有勾，需要對一次

- 文件裡有不少寫給 Claude Code 看的任務指示，開源時要決定留不留

## 主題 1 · Agent 登入方式的合規性

**問題**：這個工具自己不處理登入，只呼叫使用者本機已經登入的 CLI。自己用沒有問題；散布給別人用時，各家允不允許？

2026-11-20 查各家的官方文件。下面分成【文件】（頁面上寫的）與【未確認】（頁面沒寫或打不開）。這是整理文件的內容，不是法律意見。

### Claude Code（目前用官方的 Agent SDK）

- 【文件】Agent SDK 的說明頁寫明：除非事先取得許可，Anthropic 不允許第三方開發者在自己的產品中提供 claude.ai 登入或其用量額度，並明確包含用 Agent SDK 做的 agent；要改用 API key。（`code.claude.com/docs/en/agent-sdk/overview`）
- 【未確認】文件沒有區分「產品自己提供 claude.ai 的登入流程」和「工具只是沿用使用者自己在本機登入好的狀態」。「提供」的範圍沒有定義。
- 【未確認】文件沒有寫怎麼申請許可。
- 【文件】驗證來源的優先順序：雲端供應商的憑證 → `ANTHROPIC_AUTH_TOKEN` → `ANTHROPIC_API_KEY` → `apiKeyHelper` → `CLAUDE_CODE_OAUTH_TOKEN` → 訂閱登入。也就是說環境裡有 API key 時會優先用它。（`code.claude.com/docs/en/authentication`）
- 【文件】`claude setup-token` 產生的 token 是給無法用瀏覽器登入的 CI 與腳本用的，用的是訂閱額度。
- 【文件】沒有找到限制「用訂閱在腳本或背景服務裡執行 Claude Code」的條文。

### Codex（目前用 subprocess 包 `codex exec`）

- 【文件】兩種登入：ChatGPT 帳號（訂閱額度）與 API key（依用量計費）。`codex exec` 預設沿用已儲存的登入，可以用 `CODEX_API_KEY` 單次指定。
- 【文件】官方建議自動化的情境用 API key，但沒有要求；用 ChatGPT 登入跑 CI 被列為可行的替代做法，並提醒不要用在公開或開源的 repo 上（指的是在 CI 裡放登入憑證這件事）。
- 【文件】沒有找到限制第三方工具包裝 `codex exec` 或沿用使用者 ChatGPT 登入的條文。
- 【未確認】文件的側邊欄有一個「ChatGPT plan usage」的章節，標題看起來是講開源應用程式如何使用使用者的 ChatGPT 方案，但那幾個頁面打不開（404），內容沒有讀到。
- Codex CLI 本身是 Apache-2.0。

### Gemini CLI（還沒做）

- 【文件】README 與文件的橫幅寫明：免費的個人方案與 Google AI Pro / Ultra 已在 2026-06-18 移到 **Antigravity CLI**，Gemini CLI 現在只給 Gemini Code Assist 的企業方案與既有的付費 API / Vertex 金鑰使用。
- 【文件】條款寫明：用第三方的軟體或工具直接存取 Gemini CLI 背後的服務是違反條款的，可能導致帳號被停用。
- 【文件】技術上它適合被程式驅動：有非互動模式（`-p`）、JSONL 的事件輸出（`--output-format stream-json`）、可以用 session id 續接（`--resume`）、有 sandbox 與核准模式、會回報 token 用量。非互動的環境建議用 API key 或 Vertex AI。
- 【未確認】沒有實際執行過；事件的欄位名稱與收到訊號時的行為要實測。Antigravity CLI 完全沒有調查。

### 目前的判讀（待確認）

1. **「使用者自己在 terminal 登入，工具只偵測」這個做法本身沒有被任何一家明文禁止**，Codex 這邊最明確。
2. **Claude 是唯一有明文限制的**，而且剛好落在灰色地帶：條文針對的是「提供 claude.ai 登入」，沒說沿用使用者本機的登入算不算。
3. **Gemini 的情況變了**：個人使用者現在要用的是 Antigravity CLI，而且條款對第三方工具的態度是三家裡最嚴的。

### 結論

**Claude 的登入方式**（決策第 140 筆）

- 開源版本的文件與設定頁，預設引導使用者設定 `ANTHROPIC_API_KEY`。這是條文明確允許的路。
- 沿用本機訂閱登入的做法保留、照常可以用，工具不擋。設定頁偵測到只有訂閱登入時顯示一段說明：條文的內容、它沒有講清楚的地方、由使用者自己判斷。
- 工具本身不處理任何憑證：不做登入流程，不儲存 token 或 API key，只檢查「能不能用」。API key 由使用者放在自己的環境變數裡。
- 沒有選的：只允許 API key（現有的使用方式會壞掉）；完全不提條文（把風險無聲地留給使用者）。
- 之後可以另外向 Anthropic 詢問這種用法需不需要許可；有結果再調整預設。這不擋進度。

**第一版支援的 agent**（決策第 141 筆）

- Claude Code 與 Codex 兩種。
- Gemini 不進第一版：個人使用者現在要用的是 Antigravity CLI，得從頭調查；條款對第三方工具的限制也是三家裡最嚴的。設定頁的架構留好加第三種 agent 的位置。

## 主題 2 · 定位

**問題**：`00-vision.md` 自己寫了「核心迴圈本身不是差異點」，Agent Orchestrator 已經做了同樣的事。開源之後，別人為什麼要用這個？

### 和 Agent Orchestrator 的差異

對方的資料是從官網與文件讀來的，沒有實際裝來用過；「沒查到」不等於「沒有」。

| | Agent Orchestrator | agent-supervisor |
| --- | --- | --- |
| 形式 | 桌面應用程式（Electron） | 本機 daemon 加瀏覽器，有 CLI 與 HTTP API |
| 合併 PR | 可以在 app 內合併 | 要去 GitHub |
| 每個專案的主 agent（拆任務） | 有 | 沒有 |
| 內嵌 terminal、聊天 | 有 | 沒有 |
| 防迴圈的上限 | 文件沒有提到次數或花費上限 | 修復、留言處理、花費、token、執行時間都有硬上限 |
| 稽核紀錄 | 沒查到 | 只增不改的事件表 |
| 設計文件 | 沒查到 | 每個決定都記了理由與沒選的方案 |
| 授權 | Apache-2.0 | Apache-2.0 |

功能的廣度上對方領先。

### 考慮過的三種定位

| 定位 | 主打 |
| --- | --- |
| 甲. 可稽核、有上限 | 硬上限、不可改的事件紀錄、權限政策 |
| 乙. 可以拿來改 | adapter 介面乾淨、有 HTTP API 與 CLI、設計決策全部公開 |
| 丙. 功能追上對方 | 功能齊全 |

### 結論（決策第 142 筆）

**先做乙，再做丙。**

- **乙階段的目標**：一個不認識作者的開發者，能裝起來、看得懂、接上自己的 agent。
- **丙階段**：補上功能的廣度（合併按鈕、同時執行數上限與排隊、自動派工、內嵌 terminal、桌面版）。順序等乙做完、有了使用者的回饋再排。
- 乙是丙的地基：別人看得懂、接得上，才會有人幫忙補功能。
- 第一批使用者暫時假設是想自己動手改的個人開發者（還沒有確認）。

**乙階段要做到的事與現在的缺口**

| 要做到 | 現在缺什麼 |
| --- | --- |
| 裝得起來 | README、安裝流程、前端檔案打包、啟動時檢查相依工具 |
| 知道自己能用哪些 agent | 設定頁與偵測 |
| 看得懂怎麼運作 | 對外的架構說明 |
| 接得上自己的 agent | adapter 的開發指南與一個最小範例 |
| 能用程式操作它 | HTTP API 的說明與穩定性承諾；CLI 名稱定案 |
| 敢送 PR | 這個 repo 自己的 CI、貢獻指南 |
| 不會一用就卡死 | 盤點裡「會卡住」的那五項 |

**原本 roadmap 的階段在這個定位下的位置**

- 階段 4（自動派工）、階段 7（桌面版）：屬於丙，往後。
- 階段 6（自製 API agent）：提前並縮小，當成「adapter 怎麼寫」的示範，也對應「直接使用 endpoint」那一類 agent。只做到能當範例的程度。
- 階段 5（治理）：不是主打，往後。但信任模型的洞要在對外的文件裡講清楚。

## 主題 4 · 語言與平台

### 語言（決策第 143 筆）

**對外的東西全部英文，內部的設計文件維持中文。**

| 改成英文 | 維持中文 |
| --- | --- |
| README、安裝與使用說明 | `docs/` 下現有的設計文件：決策紀錄、規格、各階段任務單、調查筆記 |
| adapter 的開發指南、API 說明、貢獻指南 | 這份規劃文件 |
| 介面上的文字（目前有一部分提示是中文） | |
| 程式裡的註解與 docstring（約 5,000 行程式） | |

- 定位是「讀得懂、可以拿來改」，打開程式碼看到讀不懂的註解會和定位衝突，所以註解也要翻。
- 設計文件不翻：它們是這個專案的歷史紀錄，翻譯的成本高，之後也還要繼續用中文寫。README 裡說明它們是中文的。
- 註解的翻譯要早做：之後新寫的程式直接用英文，不要寫了中文再翻一次。`CLAUDE.md` 的「註解與文件用繁體中文」要跟著改。

### 平台（決策第 144 筆）

**支援 macOS 與 Linux，不支援 Windows。**

- 這個 repo 的 CI 會跑在 GitHub Actions 的 Linux 上，測試本來就得在 Linux 上過，等於順便驗證。
- 五個用了平台相關功能的模組（`recovery.py`、`daemon.py`、`cli.py`、`notifier.py`、`adapters/codex.py`）要在 Linux 上確認。
- 通知在 Linux 上要另外的做法，或先不發。
- Windows 要重寫訊號、程序群組、檔案鎖；文件裡寫明不支援、可以用 WSL。

## 主題 5 · 開源的時機與第一版的範圍

### 第一版的範圍（決策第 145 筆）

| # | 項目 | 內容 |
| --- | --- | --- |
| 1 | 這個 repo 的 CI | GitHub Actions 跑 pytest、ruff、前端測試與 build，macOS 與 Linux 都跑 |
| 2 | 英文化 | 註解與 docstring、介面文字；`CLAUDE.md` 的慣例跟著改 |
| 3 | Linux 支援 | 五個平台相關的模組在 Linux 上確認並修正 |
| 4 | 安裝 | 從 GitHub 一行指令裝得起來、前端檔案由 CI 打包並附在 GitHub Release 上、啟動時檢查 `gh` 與各 agent |
| 5 | Agent 設定頁 | 偵測安裝與登入狀態、API key 的引導、條文的說明 |
| 6 | 對外的文件 | README、使用說明、信任模型與已知限制、貢獻指南 |
| 7 | 修掉「會卡住」的五項 | PR 重新開啟、無法結案的任務、中斷後的殘留、改寫歷史、超過上限後不能送訊息 |
| 8 | Adapter 開發指南與範例 | 介面說明、一個最小的範例 adapter、HTTP API 的說明 |

**不進第一版**：直接打 endpoint 的 agent（原本的階段 6）。它要自己寫 agent 迴圈、工具與 context 管理，是最大、風險最高的一項，會把公開的時間拖很久。第 8 項的範例先用一個很小的假 agent 示範介面，真正的 endpoint agent 當成公開後的第一個大功能。

### 時機與版本號（決策第 146 筆）

- 做完上面八項才把 repo 設成公開，同時發版。別人第一眼看到的要是裝得起來、文件齊全的東西。
- 公開的那一版是 `0.3.0`，不是 `1.0`：`0.x` 表示介面還可能變動。HTTP API 與 adapter 介面在有外部使用者之前不承諾穩定。

### 名稱與發布方式（決策第 147、148 筆）

**不發布到 PyPI，從 GitHub 安裝；專案、repo、import 名稱都維持不變；指令暫定改成 `agsv`。** 下面是查詢的過程與考慮過的名字。

2026-11-20 查 PyPI：

| 名稱 | 現況 |
| --- | --- |
| `agent-supervisor`（套件名） | 已經被別人註冊：0.3.0，「Policy-driven process isolation and supervision for agent runtimes」，領域很接近 |
| `asv`（指令名） | Airspeed Velocity，知名的 Python 效能測試工具，指令也叫 `asv` |

所以套件名與指令名都要另外取，而且要在公開前定案。對方的套件很可能也用 `agent_supervisor` 當 import 名稱，兩個裝在同一個環境會互相蓋掉，所以 import 名稱最好一起改。

候選（都查過 PyPI 與 Homebrew 沒有同名的；PyPI 會把去掉連字號後相同的名稱視為重複，所以 `agent-warden`、`agent-foreman`、`agent-board`、`agent-loop` 雖然查不到，實際上註冊不了）：

| 候選 | 指令 | 意思 | 取捨 |
| --- | --- | --- | --- |
| `agentherd` | `agentherd` | 趕一群 agent | 一看就懂在做什麼，好記。指令有點長；不用 `herd` 當指令是因為 Laravel Herd 用了 |
| `prloop` | `prloop` | PR 的回饋迴圈 | 最短，點出核心機制。但看不出「多個 agent」與「看板」 |
| `worktender` | `worktender` | 照顧 worktree 的人 | 獨特、不會撞名。第一次看不容易懂 |
| `agentsup` | `agentsup` | agent-supervisor 的縮寫 | 和現在的名稱最接近，改動感最小。唸起來不順，也仍然容易和 PyPI 上那個搞混 |

還沒有查的：網域、商標。

後來又查了三個方向，約一百二十個名字：

- **指揮、調度**（orchestrator、conductor）：貼切的字都被同類工具用了。`ai-orchestrator`、`agent-orchestrator` 已被註冊；Conductor 是另一個同類工具的名字。
- **派工**（`agent-dispatcher`）：可以註冊，但 `agent-dispatch` 只差一個字母、領域又接近；而且派工只講到開頭，這個工具的重點在派出去之後。
- **監工與發包**：這個工具做的事和營造業的發包流程幾乎一對一（發包、各工班在自己的工區施工、監工、驗收不過叫回來修、驗收通過業主簽收），所以 supervisor 與 foreman 才是對的字。可以註冊的有 `site-supervisor`、`site-foreman`、`pr-supervisor`、`fleet-supervisor`、`agent-overseer`、`clerk-of-works` 等。

**最後的決定**是不換掉 supervisor 這個字，也不發布到 PyPI（第 148 筆）：

- 安裝方式是從 GitHub：`uv tool install git+https://github.com/<owner>/agent-supervisor`，或下載 GitHub Release 上附的套件檔。想改程式的人 clone 或 fork。
- 不上 PyPI 就不需要套件名，名稱的問題直接消失；也少一條要維護的發布流程。定位是「讀得懂、可以拿來改」，這種專案的使用者本來就會 clone。
- 之後想上 PyPI 的話，`ai-agent-supervisor` 在 2026-11-20 查過是可以註冊的（PyPI、npm、Homebrew 都沒有同名的）。
- 前端的檔案由 CI build 好、打包進套件、附在 GitHub Release 上，只想用的人不需要 Node.js。

| 名稱 | 值 | 說明 |
| --- | --- | --- |
| 專案 / repo | `agent-supervisor` | 不變 |
| PyPI 套件 | 不發布 | 之後要發的話用 `ai-agent-supervisor` |
| import 名稱 | `agent_supervisor` | 不變。PyPI 上那個 `agent-supervisor` 裝進去的模組也叫這個名字，兩個裝進同一個環境會互相蓋掉；但這個工具是獨立執行的應用程式，建議的安裝方式會給它自己的環境，在文件裡註明即可 |
| 指令 | 暫定 `agsv` | `asv` 和 Airspeed Velocity 的指令相同，而指令不管怎麼裝最後都在同一個 `PATH` 上，躲不掉。做到「安裝與打包」那個任務時才改 |
