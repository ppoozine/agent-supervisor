# 01 · 分階段規劃

最後更新：2026-11-22

階段 0 到 2（含 1.5）是 MVP（版本 `0.1`），之後是正式版（到 `1.0`）。每個階段都有「完成標準」，沒達到就不進下一階段。

MVP 確認可行之後，方向從「學習與自己使用」改成**開源給別人用**：先做到讀得懂、可以自己接 agent，再補功能的廣度（見 `03-decisions.md` 第 142 筆）。階段 4 之後的順序在 2026-11-20 依這個方向重排過（第 149 筆），規劃的過程見 `09-open-source-plan.md`；`0.3` 發布後在 2026-11-22 再排一次（第 174 筆），規劃見 `11-next-plan.md`。

## 階段 0 · 準備

**目標**：開始寫程式前，環境與文件都到位。

- 建立 `agent-supervisor` 與 `agent-supervisor-sandbox` 兩個 private repo
- 本機確認：Python 3.13+、`uv`、`gh`（已登入）、`claude` CLI、`codex` CLI
- 把 `CLAUDE.md` 與 `docs/` 放進主專案並 commit 到 main

**完成標準**：在主專案資料夾啟動 Claude Code，它能讀到 `CLAUDE.md` 並正確說出目前在哪個階段。

---

## 階段 1 · 核心迴圈（MVP 前半）

**目標**：證明整個產品最核心的假設成立，先不做任何介面。

動工前先做一次 Codex 介面的調查（任務 0，只調查不實作），確認 adapter 介面裝得下第二種 agent，再開始實作。

分三步，細節見 `02-mvp-spec.md`，任務單見 `04-phase1-tasks.md`：

1. **Adapter + Runner**：用官方 SDK 啟動一個 Claude Code session，把事件寫進資料庫，記下 token 與花費，套用基本權限政策，並處理 daemon 重啟後的復原。
2. **Worktree + run 收尾**：每個任務建獨立 worktree 與 branch；agent 正常結束的每一次 run 之後由 supervisor commit、push，第一次時開 PR。
3. **Poller + Dispatcher**：輪詢 CI 狀態，失敗時把 log 餵回同一個 session，含防迴圈規則。

**完成標準**：在 sandbox repo 開一個「會讓測試失敗」的任務，不需要人介入，最後 CI 變綠燈；另外刻意製造一個修不好的任務，確認它在 3 次後停下來。

**主要風險**
- SDK 的串流、續接、權限控制的行為和預期不同 → 第 1 步先做調查並記錄。
- SDK 在訂閱方案登入下能不能這樣用還沒查證 → 第 1 步一併確認；不行的話改用 API key，或重新評估第 16 筆決定。
- CI log 太長，直接餵回會爆 context → 只擷取失敗的部分。

## 階段 1.5 · 第二個 adapter

**目標**：用第二個實作驗證 adapter 介面站得住。只有一個實作的介面一定會偏向那個實作。

- 用 subprocess 包 `codex exec`（決策第 48 筆），先查明 `codex-notes.md`「還沒查明的事」中屬於這條路線的項目
- 實作 Codex adapter，並如實填寫它的 `capabilities`
- 介面不合用的地方回頭修介面，Runner 仍然不得出現任何 agent 專屬的字串

**完成標準**：
- 共同必測：階段 1 驗證清單中不依賴特定能力的項目，用 Codex 重跑一次並通過
- 依能力而定：Codex 支援的能力（例如續接、輪數上限）各自通過對應的驗證
- 做不到的能力：`capabilities` 如實標示，並驗證對應的降級行為（例如只靠執行時間上限擋下）
- Runner、Dispatcher、Poller 的程式碼不需要因為 agent 種類而分支

**主要風險**（依任務 0 的實測）：
- Codex 不回報花費，也沒有輪數與花費上限 → 用 `capabilities` 表達，靠 token 上限、修復次數與執行時間上限擋住。
- 被中止的 run 拿不到用量，用量又是整個 session 的累計值 → adapter 自己相減，拿不到時記為未知。
- 有些被 sandbox 擋下的指令不會出現在事件流裡 → Codex 任務的稽核紀錄不完整，在規格裡寫明。
- 中止要用 SIGINT；用 SIGTERM 的話子程序會留下來 → 中止流程仍要確認子程序真的結束。

## 階段 2 · 看板介面（MVP 後半）

**目標**：把階段 1 的能力變成別人看得懂、可以操作的東西。

- **API + SSE**：十二個端點（含 SSE），推送狀態與 log。
- **React 看板**：四欄看板、任務詳情頁（log、事件紀錄、花費）、開任務的表單（可選 agent）。版面與卡片內容見 `05-ui-reference.md`。

**完成標準**：從瀏覽器開一個任務，能看到卡片隨著狀態變化移動到對應的欄位、即時看到 agent 輸出、查到這個任務花了多少錢。到這裡發 `0.1`，MVP 完成。

**狀態**：2026-11-19 完成，驗證清單見 `07-phase2-tasks.md`，版本 `0.1.0`。

**主要風險**：前端花掉太多時間。介面只求可用，不做美化。

---

## 階段 3 · 回饋迴圈補齊

**目標**：除了 CI，其他會打斷流程的事件也自動處理。

- PR 上的留言 → 轉回負責的 agent（觸發條件是「有新的留言」，見 `03-decisions.md` 第 119 筆）
- Merge conflict → 請 agent 解衝突（用 merge，不用 rebase）
- 卡片進 Needs you 時發通知（macOS 的系統通知）
- 任務詳情頁內直接看 diff
- 有了 diff 檢視之後，再評估要不要在詳情頁加合併按鈕（見 `03-decisions.md` 第 114 筆）。評估已完成，要不要做還沒決定，記在「尚未決定」

**完成標準**：一個 PR 從開出到可合併，中間經過一次 CI 失敗、一次留言要求修改，人只做了「留言」和「按合併」兩個動作。任務單見 `08-phase3-tasks.md`。

**狀態**：2026-11-19 完成，完成標準已在 sandbox 實測通過，版本 `0.2.0`。

---

## 階段 4 · 開源準備

**目標**：一個不認識作者的開發者，能把它裝起來、看得懂、接上自己的 agent。

任務單見 `10-phase4-tasks.md`，一次做一個任務、合併後才做下一個：

1. 這個 repo 自己的 CI（macOS 與 Linux）
2. Linux 支援
3. 英文化：程式裡的註解、介面文字；`docs/` 下的設計文件維持中文
4. 修掉會讓任務卡住、只能人工處理的五個問題
5. Agent 設定頁：偵測每一種 agent 與 `gh` 能不能用，引導使用者自己在 terminal 登入
6. 安裝與打包：從 GitHub 安裝，前端的檔案由 CI 打包；不發布到 PyPI
7. Adapter 開發指南、最小的範例 adapter、HTTP API 的說明
8. 對外的文件；把 repo 設成公開

**完成標準**：一個沒看過這個專案的人，只照 README 做，在 15 分鐘內裝好並跑完第一個任務；另外照 adapter 指南、不改這個 repo 的程式，能讓 daemon 載入一個外部的 adapter。到這裡把 repo 設成公開，發 `0.3`。

**主要風險**
- 英文化的變更很大，容易夾帶行為的改變 → 這個任務只翻譯，不改識別字與邏輯，測試數量前後要一樣。
- 沒有 Linux 的機器 → 只能靠 CI 驗證，沒驗到的行為要寫明。
- Claude Agent SDK 的文件不允許第三方產品提供 claude.ai 登入 → 預設引導使用者用 API key，沿用本機登入的做法保留並附上條文的說明（第 140 筆）。
- HTTP API 與 adapter 介面公開後就有人依賴 → `0.x` 期間寫明不承諾穩定。

**狀態**：2026-11-22 完成，repo 已公開，版本 `0.3.0`。

## 階段 5 · 新介面

**目標**：介面從「只求可用」變成每天願意用的樣子，並且在一個任務裡就能看到 agent 的對話、自己在 worktree 裡動手。

規劃見 `11-next-plan.md` 主題 1、4、5，任務單等規劃合併後再寫：

1. 裝 Tailwind（獨立的小 PR；Codex 在 agsv 的 sandbox 裡可能不能連網）
2. UI 需求文件：版面、每一頁的內容、Chat / Shell / 主 agent 的預留位置、design tokens
3. UI 改版：用 agsv 開 Codex 的任務實作。第一張只做外觀（design tokens、看板、任務詳情頁），確認視覺後再補其他畫面
4. Chat：把 Log 改成對話的樣子，資料仍來自 `events` 表；一則訊息仍然對應一次 run
5. Shell：在任務的 worktree 開 PTY，前端用 xterm.js；永遠不控制 agent

**完成標準**：在新介面開一個任務，從對話看懂 agent 做了什麼、追加一則訊息，在同一頁的 shell 跑一次測試，全程不需要離開這一頁；介面經過作者的視覺驗收。到這裡發 `0.4`。

**主要風險**
- 內嵌 shell 等於透過 HTTP 執行任意指令 → WebSocket 檢查 `Origin` 與 `Host`，沿用 `api/guard.py` 的規則，並加測試。
- 交給 Codex 的改版夾帶資料流或 API 的改動 → 第一張任務限定只改外觀，code review 時檢查。
- PTY 在 macOS 與 Linux 的行為不同 → 預計用標準庫的 `pty`，不另裝套件（不支援 Windows，和第 144 筆一致），兩個平台都在 CI 跑；在任務單裡確認。

## 階段 6 · 主 agent 派工

**目標**：從「一次手動開一張單」擴大到「給一個目標，自動拆成多張單」。

- 全域的同時執行數上限與排隊。先做，否則一次拆出很多任務會同時燒掉大量用量
- 主 agent：每個專案一個，把目標拆成多個任務，可以指定各任務用哪一種 agent
- 第一版拆完要人確認才派工；拆出來的任務走現有的流程，各自有 worktree、上限與事件紀錄

**完成標準**：給一個需要動到三個以上檔案群的目標，主 agent 拆成數個任務，確認後平行進行，同時執行的數量不超過上限，其餘排隊；彼此的 PR 不互相衝突或能自動解決。到這裡發 `0.5`。

**主要風險**：拆任務拆錯、任務之間互相依賴。這是整個專案最難的部分，先做最保守的版本（拆完讓人確認再派工）。主 agent 開任務的方式在任務單裡比較。

## 階段 7 · 桌面版

**目標**：不會用 terminal 的人也裝得起來。

- 桌面安裝檔：殼用 Tauri（第 5 筆）或 Electron，在任務單裡決定
- Python 的 daemon 包成 sidecar
- macOS 的簽章與公證

**完成標準**：一個不會用 terminal 的人，下載安裝檔後在 15 分鐘內跑完第一個任務。到這裡發 `0.6`。

**主要風險**
- Python 打包成單一執行檔很費工，而且 agent 的 CLI（`claude`、`codex`）、`gh` 仍然要使用者自己裝。
- 不簽章的話 macOS 第一次打開會被擋下 → 需要 Apple Developer 帳號（一年 99 美元），還沒決定。

---

## 階段 8 · 補功能的廣度

**目標**：補上同類工具有、而這裡沒有的常用功能。

- 在看板內合併 PR（合併的方式要不要可選還沒決定）
- 專案設定頁：基底分支、是否要求 review 可以從介面改
- PR 合併後自動清掉 worktree
- 從 GitHub issue 自動建任務；輪詢改成 webhook（可選）
- 接手模式：在 agent 本身的 TUI 裡操作，期間暫停自動處理（`11-next-plan.md` 主題 1 的 B）。等 Chat 用過、確定不夠用再決定要不要做
- 其餘依公開後使用者的回饋決定

**完成標準**：一個任務從開出到合併，全程不需要離開看板。

---

## 階段 9 · 直接打 endpoint 的 agent

原本排在階段 5，2026-11-22 往後挪（第 174 筆），內容不變。

**目標**：直接呼叫模型 API，自己寫一個最小的 coding agent，當作第三個 adapter。它同時是「adapter 怎麼寫」最完整的示範，也讓使用者可以接任何相容的模型 endpoint。API key 由使用者放在環境變數，工具不儲存。可以自由更換模型，每一步都由自己的程式控制。

- 最小工具集：讀檔、寫檔、執行指令
- 自己的 agent 迴圈、對話紀錄保存與續接
- 權限政策與核准關卡直接在迴圈裡執行
- 用量與花費由 API 回應計算

**完成標準**：用自製 agent 在 sandbox 跑通階段 1 的驗證清單；更換模型只需要改設定。

**主要風險**：這等於另一個專案。context 過長時的處理、錯誤復原、工具設計都要自己來。範圍只求跑通，不追求和現成 agent 一樣好用。

---

## 階段 10 · 治理

**目標**：敢把這個工具用在真正的 repo 上。

- 權限政策：哪些指令、哪些路徑 agent 不能碰，可依專案設定
- 人工核准關卡：特定動作要人按同意才繼續。只有 `can_gate_tool_calls` 為真的 adapter 支援
- 預算：每個專案、每個任務的花費上限與警示
- 稽核查詢：依時間、任務、事件類型搜尋紀錄，可匯出
- 隔離升級：從 worktree 改為 container sandbox

**完成標準**：能回答「上週哪個 agent 在哪個任務執行了哪些指令、花了多少錢」，並能示範一個被政策擋下的動作。

## 檢查點

**做完階段 2（MVP）後**（2026-11-19 到 20）：確認可行，方向改成開源給別人用，階段 4 之後重排。

**做完階段 5 後**再看一次：

- 公開之後實際有人用嗎？他們最常卡在哪裡、最常問什麼？
- 有沒有人照指南接了自己的 agent？指南哪裡不夠？階段 9 要不要提前？
- Chat 夠不夠用，接手模式要不要做？

多人使用、登入、角色權限要不要做，以及什麼才算 `1.0`，留到階段 7 之後再決定（見 `03-decisions.md` 第 30 筆）。
