# 01 · 分階段規劃

最後更新：2026-11-19

共九個階段。階段 0 到 2（含 1.5）是 MVP（版本 `0.1`），階段 3 到 7 是正式版（到 `1.0`）。每個階段都有「完成標準」，沒達到就不進下一階段。

這個專案的主要目的是學習與自己使用（見 `03-decisions.md` 第 17 筆），階段的取捨以此為準。

## 總覽

| 階段 | 名稱 | 產出 | 版本 |
| --- | --- | --- | --- |
| 0 | 準備 | 兩個 repo、工具就緒、文件入庫 | – |
| 1 | 核心迴圈 | 不含介面，在 terminal 跑通「開任務 → PR → CI 失敗 → 自動修」 | – |
| 1.5 | 第二個 adapter | Codex adapter，跑通同一套核心迴圈 | – |
| 2 | 看板介面 | API、SSE、React 四欄看板 | `0.1`（MVP 完成） |
| 3 | 回饋迴圈補齊 | Review 留言、merge conflict、通知、diff 檢視 | `0.2` |
| 4 | 自動派工 | Orchestrator 拆任務、issue 觸發 | `0.3` |
| 5 | 治理 | 權限政策、核准關卡、預算、稽核查詢、sandbox | `0.4` |
| 6 | 自製 API agent | 直接呼叫模型 API 的第三個 adapter | `0.5` |
| 7 | 產品化 | 桌面安裝檔、安裝文件 | `1.0` |

---

## 階段 0 · 準備

**目標**：開始寫程式前，環境與文件都到位。

- 建立 `agent-supervisor` 與 `agent-supervisor-sandbox` 兩個 private repo
- 本機確認：Python 3.13+、`uv`、`gh`（已登入）、`claude` CLI、`codex` CLI
- 把 `CLAUDE.md` 與 `docs/` 放進主專案並 commit 到 main

**完成標準**：在主專案資料夾啟動 Claude Code，它能讀到 `CLAUDE.md` 並正確說出目前在哪個階段。

---

## 階段 1 · 核心迴圈（MVP 前半）

**目標**：證明整個產品最核心的假設成立，先不做任何介面。

動工前先做一次 Codex 介面的調查（任務 0，只調查不實作），確認 adapter 介面裝得下第二種 agent，再開始實作。

分三步，細節見 `02-mvp-spec.md`，任務單見 `04-phase1-tasks.md`：

1. **Adapter + Runner**：用官方 SDK 啟動一個 Claude Code session，把事件寫進資料庫，記下 token 與花費，套用基本權限政策，並處理 daemon 重啟後的復原。
2. **Worktree + run 收尾**：每個任務建獨立 worktree 與 branch；agent 正常結束的每一次 run 之後由 supervisor commit、push，第一次時開 PR。
3. **Poller + Dispatcher**：輪詢 CI 狀態，失敗時把 log 餵回同一個 session，含防迴圈規則。

**完成標準**：在 sandbox repo 開一個「會讓測試失敗」的任務，不需要人介入，最後 CI 變綠燈；另外刻意製造一個修不好的任務，確認它在 3 次後停下來。

**主要風險**
- SDK 的串流、續接、權限控制的行為和預期不同 → 第 1 步先做調查並記錄。
- SDK 在訂閱方案登入下能不能這樣用還沒查證 → 第 1 步一併確認；不行的話改用 API key，或重新評估第 16 筆決定。
- CI log 太長，直接餵回會爆 context → 只擷取失敗的部分。

---

## 階段 1.5 · 第二個 adapter

**目標**：用第二個實作驗證 adapter 介面站得住。只有一個實作的介面一定會偏向那個實作。

- 用 subprocess 包 `codex exec`（決策第 48 筆），先查明 `codex-notes.md`「還沒查明的事」中屬於這條路線的項目
- 實作 Codex adapter，並如實填寫它的 `capabilities`
- 介面不合用的地方回頭修介面，Runner 仍然不得出現任何 agent 專屬的字串

**完成標準**：
- 共同必測：階段 1 驗證清單中不依賴特定能力的項目，用 Codex 重跑一次並通過
- 依能力而定：Codex 支援的能力（例如續接、輪數上限）各自通過對應的驗證
- 做不到的能力：`capabilities` 如實標示，並驗證對應的降級行為（例如只靠執行時間上限擋下）
- Runner、Dispatcher、Poller 的程式碼不需要因為 agent 種類而分支

**主要風險**（依任務 0 的實測）：
- Codex 不回報花費，也沒有輪數與花費上限 → 用 `capabilities` 表達，靠 token 上限、修復次數與執行時間上限擋住。
- 被中止的 run 拿不到用量，用量又是整個 session 的累計值 → adapter 自己相減，拿不到時記為未知。
- 有些被 sandbox 擋下的指令不會出現在事件流裡 → Codex 任務的稽核紀錄不完整，在規格裡寫明。
- 中止要用 SIGINT；用 SIGTERM 的話子程序會留下來 → 中止流程仍要確認子程序真的結束。

---

## 階段 2 · 看板介面（MVP 後半）

**目標**：把階段 1 的能力變成別人看得懂、可以操作的東西。

- **API + SSE**：十二個端點（含 SSE），推送狀態與 log。
- **React 看板**：四欄看板、任務詳情頁（log、事件紀錄、花費）、開任務的表單（可選 agent）。版面與卡片內容見 `05-ui-reference.md`。

**完成標準**：從瀏覽器開一個任務，能看到卡片隨著狀態變化移動到對應的欄位、即時看到 agent 輸出、查到這個任務花了多少錢。到這裡發 `0.1`，MVP 完成。

**狀態**：2026-11-19 完成，驗證清單見 `07-phase2-tasks.md`，版本 `0.1.0`。

**主要風險**：前端花掉太多時間。介面只求可用，不做美化。

---

## 階段 3 · 回饋迴圈補齊

**目標**：除了 CI，其他會打斷流程的事件也自動處理。

- PR 上的留言 → 轉回負責的 agent（觸發條件是「有新的留言」，見 `03-decisions.md` 第 119 筆）
- Merge conflict → 請 agent 解衝突
- 卡片進 Needs you 時發通知
- 任務詳情頁內直接看 diff
- 有了 diff 檢視之後，再評估要不要在詳情頁加合併按鈕（見 `03-decisions.md` 第 114 筆）

**完成標準**：一個 PR 從開出到可合併，中間經過一次 CI 失敗、一次留言要求修改，人只做了「留言」和「按合併」兩個動作。任務單見 `08-phase3-tasks.md`。

---

## 階段 4 · 自動派工

**目標**：從「一次手動開一張單」擴大到「給一個目標，自動拆成多張單」。

- 全域的同時執行數上限與排隊：自動派工之前必須先有，否則一次拆出很多任務會同時燒掉大量用量
- Orchestrator：把大目標拆成多個任務並派工，可以指定各任務用哪一種 agent
- 從 GitHub issue 自動建任務
- 輪詢改成 webhook（可選）

**完成標準**：給一個需要動到三個以上檔案群的目標，工具自動拆成數個任務平行進行，彼此的 PR 不互相衝突或能自動解決。

**主要風險**：拆任務拆錯、任務之間互相依賴。這是整個專案最難的部分，先做最保守的版本（拆完讓人確認再派工）。

---

## 階段 5 · 治理

**目標**：敢把這個工具用在真正的 repo 上。

- 權限政策：哪些指令、哪些路徑 agent 不能碰，可依專案設定
- 人工核准關卡：特定動作要人按同意才繼續。只有 `can_gate_tool_calls` 為真的 adapter 支援
- 預算：每個專案、每個任務的花費上限與警示
- 稽核查詢：依時間、任務、事件類型搜尋紀錄，可匯出
- 隔離升級：從 worktree 改為 container sandbox

**完成標準**：能回答「上週哪個 agent 在哪個任務執行了哪些指令、花了多少錢」，並能示範一個被政策擋下的動作。

---

## 階段 6 · 自製 API agent

**目標**：直接呼叫模型 API，自己寫一個最小的 coding agent，當作第三個 adapter。可以自由更換模型，每一步都由自己的程式控制。

- 最小工具集：讀檔、寫檔、執行指令
- 自己的 agent 迴圈、對話紀錄保存與續接
- 權限政策與核准關卡直接在迴圈裡執行
- 用量與花費由 API 回應計算

**完成標準**：用自製 agent 在 sandbox 跑通階段 1 的驗證清單；更換模型只需要改設定。

**主要風險**：這等於另一個專案。context 過長時的處理、錯誤復原、工具設計都要自己來。範圍只求跑通，不追求和現成 agent 一樣好用。

---

## 階段 7 · 產品化

**目標**：別人裝得起來。

- Tauri 桌面安裝檔
- 安裝與使用文件

多人使用、登入、角色權限要不要做，留到這個階段再決定（見 `03-decisions.md` 第 30 筆）。

**完成標準**：一個沒看過原始碼的人，照文件在 15 分鐘內裝好並跑完第一個任務。到這裡發 `1.0`。

---

## 檢查點

做完階段 2（MVP）後停下來重新評估，再決定階段 3 到 7 的順序：

- 自己實際用起來，最常卡在哪裡？
- 階段 5（治理）與階段 6（自製 agent）哪個先做？
- 要不要公開 repo？

做到階段 7 時再決定：要不要做多人使用與登入。
