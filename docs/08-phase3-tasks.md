# 08 · 階段 3 任務單

最後更新：2026-11-19

階段 3 的四個任務，對應 `01-roadmap.md` 的「回饋迴圈補齊」。做法和前兩份任務單一樣：一次做一個，每個任務一個 branch、一個 PR，測試通過才算完成。

這一階段的任務是連著做的（我的指示是依序把 7 到 10 做完），所以四個 PR 會依序疊在前一個之上，合併時照編號的順序。實作中要做的設計決定由 Claude Code 先決定並記進 `03-decisions.md`，在 PR 描述裡列出來讓我事後檢查。

任務 7、8 是核心迴圈的延伸，做法和 CI 自動修復同構：Poller 發現 → Dispatcher 建立 run → 續接同一個 session。任務 9、10 是使用體驗。

## 任務 7 · Review 留言轉回 agent

```
請先讀 CLAUDE.md 與 docs/ 下的所有文件。

實作階段 3 的第一項：PR 上的留言自動轉回負責的 agent。

範圍：
1. 先用 gh 實測 PR 上三種留言（一般留言、逐行留言、review 的
   總評）查得到什麼、各自的編號長什麼樣、機器人帳號怎麼分辨、
   還沒送出的 review 看不看得到，把結果記進規格
2. Poller 把 PR 上新的留言記成事件；同一則留言只記一次。
   機器人的留言不算。已封存的任務不抓留言
3. 有還沒處理的留言時，Dispatcher 建立一個新的 run，把留言的
   內容（作者、檔案與行號、內文）餵回同一個 session
4. 觸發條件是「有新的留言」，不是 GitHub 的 Request changes：
   PR 是用使用者自己的帳號開的，GitHub 不允許作者對自己的 PR
   要求修改（決策第 119 筆）
5. 連續留好幾則時合成一次處理：最近一輪輪詢還有新留言進來，
   就先不派工
6. 防迴圈：同一則留言只餵回一次；累計花費與 token 上限照舊
   有效；另外要有一個不靠預算的上限，並寫進規格
7. 已經處理過留言的 Changes requested 不再把卡片留在
   Needs you，也不再擋住 CI 的自動修復
8. 看板：正在處理留言的卡片在 Working，標籤要分得出是在處理
   留言；留言處理不了時進 Needs you
9. 資料表要加欄位時，舊的資料庫要能自動補上
10. 測試：用 fake adapter 與 GitHub 的替身，不真的啟動 agent

不要做：回覆留言、把留言標成已解決、merge conflict、通知、
diff 檢視。
```

**我要驗證的事**
- [x] 在 sandbox 的 PR 上留一則一般留言，不做其他動作，agent 被叫起來處理並 push 新的 commit
- [x] 留一則逐行留言（指定檔案與行號），agent 收到的內容包含檔案與行號
- [x] 同一則留言不會被處理第二次：處理完之後卡片回到 In review 或 Ready to merge，不再開新的 run
- [x] 連續留兩則留言，只開一個 run，兩則都在送給 agent 的內容裡
- [ ] 留言處理期間卡片在 Working，標籤看得出是在處理留言；Events 分頁看得到留言
- [ ] 用舊的資料庫啟動新版的 daemon，原有的任務都還在、可以正常操作
- [x] 已封存的任務有新留言時不會開 run

## 任務 8 · Merge conflict

```
請先讀 CLAUDE.md 與 docs/ 下的所有文件。

實作階段 3 的第二項：PR 和基底分支有衝突時，請 agent 解掉。

範圍：
1. 先用 gh 實測 PR 能不能合併的欄位有哪些值、剛 push 完還沒
   算出來時回什麼，把結果記進規格
2. Poller 多查「能不能合併」，存成任務的一個快取欄位；還沒算
   出來的結果不能當成有衝突，也不能當成沒有衝突
3. 有衝突時 Dispatcher 建立一個新的 run。用 merge 還是 rebase
   由你決定並記進決策；要考慮 Codex 在 worktree 裡不能 commit
4. 防迴圈：同一個 commit 的衝突只處理一次；次數上限和 CI 的
   自動修復怎麼算，寫進規格
5. 衝突沒有真的解掉（檔案裡還留著衝突標記）時，不能把它
   push 出去
6. 看板：有衝突的 PR 不能出現在 Ready to merge；正在解衝突的
   卡片在 Working；解不了時進 Needs you
7. 測試：worktree 的操作用真的 git 在暫存目錄裡測，其餘用替身

不要做：自動合併 PR、rebase 之後的 force push（如果選 merge）、
通知、diff 檢視。
```

**我要驗證的事**
- [x] 在 sandbox 製造一個衝突（任務的 PR 開著時，在 main 改同一行），卡片離開 Ready to merge
- [x] 不做其他動作，agent 被叫起來解衝突，push 之後 PR 在 GitHub 上顯示可以合併
- [x] 用 Codex 的任務跑同一個情境也解得掉
- [x] 同一個衝突不會被處理第二次
- [x] 沒有衝突的 PR 行為和以前一樣

## 任務 9 · 通知

```
請先讀 CLAUDE.md 與 docs/ 下的所有文件。

實作階段 3 的第三項：卡片進 Needs you 時通知我。

範圍：
1. 通知的管道由你提出並記進決策（系統通知、瀏覽器通知，或
   兩者）；不裝新的套件
2. 只在卡片「進入」Needs you 的那一刻通知一次，停在裡面不
   重複通知；daemon 啟動時原本就在 Needs you 的卡片不通知
3. 通知的內容：任務標題與原因（卡片上的狀態標籤）
4. 可以用設定關掉
5. 發通知失敗不能影響其他功能
6. 測試：發通知的指令用替身

不要做：通知鈴鐺、通知的歷史紀錄、其他欄位的通知、
Slack 或 email。
```

**我要驗證的事**
- [ ] 按 Stop 讓一個任務進 Needs you，收到一則通知，內容有任務標題與原因
- [x] 卡片停在 Needs you 期間不會重複通知
- [x] 重啟 daemon，原本就在 Needs you 的卡片不會再通知一次
- [x] 把設定關掉後不再通知

## 任務 10 · Diff 檢視

```
請先讀 CLAUDE.md 與 docs/ 下的所有文件。

實作階段 3 的第四項：在任務詳情頁直接看 diff。

範圍：
1. 新增一個端點回傳任務的 branch 相對於基底分支的 diff。
   資料從哪裡來（本機 git 或 GitHub）由你決定並記進決策；
   已封存的任務 worktree 不在了，但 branch 還在，也要看得到
2. diff 很大時要有上限，超過就截斷並標明
3. 詳情頁多一個 Diff 分頁：依檔案分段，新增與刪除的行用顏色
   區分；不裝新的套件
4. 任務有新的 commit 時，開著的 Diff 分頁要跟著更新
5. 還沒有任何 commit 的任務顯示「沒有變更」，不是錯誤
6. 做完後評估要不要加合併按鈕（決策第 114 筆），把評估結果
   告訴我，不要直接做

不要做：逐行留言、並排檢視、語法上色、合併按鈕。
```

**我要驗證的事**
- [x] 開一個任務，agent push 之後 Diff 分頁看得到變更，內容和 GitHub 上 PR 的 Files changed 一致
- [x] agent 再 push 一次，不重新整理，Diff 分頁跟著更新
- [x] 已封存的任務也看得到 diff
- [x] 還在跑第一個 run、沒有 commit 的任務顯示沒有變更
