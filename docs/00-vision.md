# 00 · 想做的東西

最後更新：2026-11-22

## 一句話

一個讓多個 AI coding agent 同時工作的本機工具：每個任務各自隔離，CI 失敗自動回到負責的 agent 修復，人只處理例外。

## 起點

我在社群貼文看到 Agent Orchestrator 的看板截圖：四個欄位（Working、Needs you、In review、Ready to merge），每張卡片是一個 agent 正在處理的任務，並標著 PR 與 CI 狀態。我想做同一類型的服務。

## 服務目標

使用者的角色從「寫程式的人」變成「派工與驗收的人」。具體來說，這個工具要做到五件事：

| # | 目標 | 怎樣算做到 |
| --- | --- | --- |
| 1 | **平行不互踩** | 同時開多個任務，各自在獨立的工作目錄與 branch 上進行，互不影響，也不動到我自己的工作目錄 |
| 2 | **不用一直盯** | CI 失敗時，工具自己把失敗原因送回負責的 agent 修，修好自己 push，不需要我複製貼上 |
| 3 | **一眼看到全貌** | 一個看板列出所有任務，哪個在跑、哪個卡住、哪個可以合併，欄位由實際狀態決定，不靠手動拖 |
| 4 | **不會失控** | 自動修復有次數上限、花費有上限、執行時間有上限，任何一項到頂就停下來等我 |
| 5 | **事後查得到** | 每個 agent 做過什麼、花了多少，都有只增不改的紀錄可以查 |

目標 1 到 3 解決的是原本的三個痛點，目標 4、5 是讓我敢放手讓它自己跑。

## 它解決什麼問題

同時開好幾個 AI agent 寫程式時，會遇到三件事：

1. **互相踩到**：多個 agent 改同一份工作目錄，檔案互相覆蓋。
2. **要一直盯**：CI 掛了、reviewer 留言了，都得自己複製貼上回去給對的 agent。
3. **看不到全貌**：哪個在跑、哪個卡住、哪個可以合併，散在好幾個 terminal 裡。

| 問題 | 做法 |
| --- | --- |
| 互相踩到 | 每個任務一個獨立的 git worktree 與 branch |
| 要一直盯 | 輪詢 PR / CI 狀態，CI 失敗時自動把 log 送回同一個 agent session |
| 看不到全貌 | 一個看板，卡片所在欄位由實際狀態推導，不靠手動拖曳 |

### 明確不做

- 卡片拖曳：欄位是推導出來的。
- 雲端代管：是跑在自己電腦上的工具。
- 支援所有 agent 與所有 Git 平台：先 Claude Code、Codex + GitHub。
- MVP 不自己做 coding agent：先用現成的，直接打 endpoint 的 agent 排在階段 9，當作第三個 adapter。
- 多人使用與登入：目前不做，要不要做留到最後的產品化階段再決定。

## 一張卡片的生命週期

1. 我開一個任務：描述想要的結果，送出。
2. 工具建立 worktree 與 branch，啟動 agent。卡片在 **Working**。
3. Agent 寫完，工具 push 並開 PR。卡片到 **In review**。
4. CI 失敗 → 工具把失敗 log 餵回同一個 agent，卡片回到 **Working**；修完後工具再 push。
5. 修了幾次還是不過，或超過花費上限 → 卡片到 **Needs you**，等我介入。
6. CI 綠燈（專案要求 review 時還要審查通過）→ 卡片到 **Ready to merge**，我按合併。
7. PR 合併後，卡片離開看板，進 Archive。

## 定位

一開始的目的是**學習與自己使用**（第 17 筆）。MVP 確認可行之後，方向改成**開源給別人用**（第 142 筆）：先做到別人裝得起來、看得懂、接得上自己的 agent（`0.3` 已完成），再補功能的廣度。

這個領域已經有不少同類工具（Agent Orchestrator、Conductor、Vibe Kanban、Claude Squad 等）。每個任務一個 worktree、CI 失敗自動送回 agent、review 留言自動處理，這些核心迴圈別人都有，功能的廣度目前也是對方領先。

我們的差別在於**讓人敢放手**，新增的功能都不能放掉這幾點：

- **硬上限**：修復次數、留言處理次數、花費、token、執行時間都有上限，到頂就停下來等人
- **只增不改的事件紀錄**：每個 agent 做了什麼、花了多少，事後查得到
- **先確認再派工**：主 agent 拆完任務要人確認才開始（階段 6）
- **可以拿來改**：adapter 介面、HTTP API、CLI 都有文件，每個設計決定都記了理由與沒選的方案

和 Agent Orchestrator 的比較見 `09-open-source-plan.md` 主題 2 與 `11-next-plan.md`（2026-11-22 讀了它的原始碼）。
