## 階段 6 · 主 agent 派工

**目標**：從「一次手動開一張單」擴大到「給一個目標，自動拆成多張單」。

- 全域的同時執行數上限與排隊。先做，否則一次拆出很多任務會同時燒掉大量用量
- 主 agent：每個專案一個，把目標拆成多個任務，可以指定各任務用哪一種 agent
- 第一版拆完要人確認才派工；拆出來的任務走現有的流程，各自有 worktree、上限與事件紀錄

**完成標準**：給一個需要動到三個以上檔案群的目標，主 agent 拆成數個任務，確認後平行進行，同時執行的數量不超過上限，其餘排隊；彼此的 PR 不互相衝突或能自動解決。到這裡發 `0.5`。

**主要風險**：拆任務拆錯、任務之間互相依賴。這是整個專案最難的部分，先做最保守的版本（拆完讓人確認再派工）。主 agent 開任務的方式在任務單裡比較。

## 階段 7 · 桌面版

**目標**：不會用 terminal 的人也裝得起來。

- 桌面安裝檔：殼用 Tauri（第 5 筆）或 Electron，在任務單裡決定
- Python 的 daemon 包成 sidecar
- macOS 的簽章與公證

**完成標準**：一個不會用 terminal 的人，下載安裝檔後在 15 分鐘內跑完第一個任務。到這裡發 `0.6`。

**主要風險**
- Python 打包成單一執行檔很費工，而且 agent 的 CLI（`claude`、`codex`）、`gh` 仍然要使用者自己裝。
- 不簽章的話 macOS 第一次打開會被擋下 → 需要 Apple Developer 帳號（一年 99 美元），還沒決定。

## 階段 8 · 補功能的廣度

**目標**：補上同類工具有、而這裡沒有的常用功能。

- 在看板內合併 PR（合併的方式要不要可選還沒決定）
- 專案設定頁：基底分支、是否要求 review 可以從介面改
- PR 合併後自動清掉 worktree
- 從 GitHub issue 自動建任務；輪詢改成 webhook（可選）
- 接手模式：在 agent 本身的 TUI 裡操作，期間暫停自動處理（`../history/plans/11-next-plan.md` 主題 1 的 B）。等 Chat 用過、確定不夠用再決定要不要做
- 其餘依公開後使用者的回饋決定

**完成標準**：一個任務從開出到合併，全程不需要離開看板。

## 階段 9 · 直接打 endpoint 的 agent

原本排在階段 5，2026-11-22 往後挪（第 174 筆），內容不變。

**目標**：直接呼叫模型 API，自己寫一個最小的 coding agent，當作第三個 adapter。它同時是「adapter 怎麼寫」最完整的示範，也讓使用者可以接任何相容的模型 endpoint。API key 由使用者放在環境變數，工具不儲存。可以自由更換模型，每一步都由自己的程式控制。

- 最小工具集：讀檔、寫檔、執行指令
- 自己的 agent 迴圈、對話紀錄保存與續接
- 權限政策與核准關卡直接在迴圈裡執行
- 用量與花費由 API 回應計算

**完成標準**：用自製 agent 在 sandbox 跑通階段 1 的驗證清單；更換模型只需要改設定。

**主要風險**：這等於另一個專案。context 過長時的處理、錯誤復原、工具設計都要自己來。範圍只求跑通，不追求和現成 agent 一樣好用。

## 階段 10 · 治理

**目標**：敢把這個工具用在真正的 repo 上。

- 權限政策：哪些指令、哪些路徑 agent 不能碰，可依專案設定
- 人工核准關卡：特定動作要人按同意才繼續。只有 `can_gate_tool_calls` 為真的 adapter 支援
- 預算：每個專案、每個任務的花費上限與警示
- 稽核查詢：依時間、任務、事件類型搜尋紀錄，可匯出
- 隔離升級：從 worktree 改為 container sandbox

**完成標準**：能回答「上週哪個 agent 在哪個任務執行了哪些指令、花了多少錢」，並能示範一個被政策擋下的動作。
